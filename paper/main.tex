\begin{abstract}
Whether clustered extreme scores become useful maintenance alarms is a question about \emph{where} a detector fails, not only whether it does. This paper builds a layered evaluation that separates a detector into score, threshold, extreme clusters, alarm episodes and matched events, and applies it to public industrial monitoring data. A Monte Carlo study over fourteen process families at 500 replications per cell shows the ranking of six extremal-index estimators inverting between regimes: runs and K-gaps are among the worst calibrated for an independent process and the least biased of the six once extremes genuinely cluster, so a reader seeing only near-independent processes would reject the estimators that work. Nineteen methods are then evaluated on two independent held-out compressor failures under one shared alarm policy. Measuring how well each score ranks the hour before onset against the rest of the test split, most separate well above chance on both datasets, and 25 of the 38 dataset-method rows fail only after alarm conversion: the registered recurrence score matches both failures, at 2770 and 893 alarm episodes and event precision below \(0.12\%\). A circular-shift null, which preserves each detector's episode structure while breaking its alignment to the failure, shows that detectors alarming this often match with probability above \(0.99\) regardless, so recall alone carries almost no information at these rates. A single-sensor threshold remains the strongest simple baseline, and target regions transfer directionally and only on the five of seven features with cross-dataset distributional support. One configuration is different: on MetroPT2 the failure-prototype region raises 3 alarm episodes, matches the failure, and reaches \(0.12\) false alarms per operating day. Its chance-match probability is \(0.17\) and those three episodes hold the system under warning for \(16\%\) of the test period, so the result is suggestive rather than established. On two failures, no evaluated method is shown to deliver reliable early warning, and none is shown to be incapable of it.
\end{abstract}

\section*{Code and Data Availability}

Code, configuration files, data-acquisition scripts, generated-paper tooling, and reproducibility materials are maintained in the project repository \citep{Ribeiro2026DynEvtPdmRepository}. It carries a semantic version tag, a BSD-3-Clause licence, \texttt{CITATION.cff} and \texttt{codemeta.json} metadata, release notes, and an artifact manifest recording the hash of every generated figure and table, so every number in this paper is traceable to the commit that produced it.

The repository is public, and the results in this paper correspond to the tagged release \texttt{v0.3.2}. A reader can retrieve that state, install the pinned environment from the lock file, and re-run the pipeline that produced every figure and table reported here.

That release is archived, and the software citation resolves to an immutable deposit rather than to a mutable host. The cited identifier is the concept DOI \href{https://doi.org/10.5281/zenodo.21803768}{10.5281/zenodo.21803768}, which names the software across all its versions. Every number reported in this paper was produced by release \texttt{v0.3.2}, and that version string is what pins the state rather than the DOI itself; readers who want an identifier for that snapshot alone can use its version DOI, \href{https://doi.org/10.5281/zenodo.21803769}{10.5281/zenodo.21803769}.

Citing the concept DOI is deliberate. A version DOI is minted from a snapshot after that snapshot is frozen, so an archive can never contain the identifier issued for it, and a paper pinned to one is pinned to an archive that does not describe itself. A concept DOI is fixed once and does not change, so it remains correct as the software continues, and naming the version in the text supplies the precision the identifier gives up.

Raw third-party datasets are not redistributed by this repository; the acquisition pipeline stores them locally under \texttt{data/raw/} and documents their public sources through the dataset registry.
